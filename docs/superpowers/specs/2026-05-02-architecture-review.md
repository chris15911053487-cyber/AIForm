## 2. 技术选型评审

### 2.1 整体评价：良好

NestJS + Vue3 + TypeScript + PostgreSQL + Redis + Docker 是成熟稳定的技术组合，大方向正确。

### 2.2 具体建议

| 技术 | 当前选择 | 评审意见 | 建议 |
|------|---------|---------|------|
| 后端框架 | NestJS | 模块化好但概念层次多，AI容易在DI/Guard/Interceptor配置上出错 | 制定标准模块模板 |
| 消息队列 | BullMQ | 对初期场景（异步通知/邮件）偏重 | 第一阶段可用DB轮询替代，第二阶段再引入 |
| 向量数据库 | Qdrant | 需独立容器(2-4GB内存) | 初期(<10万条)用Pgvector替代，省一个容器 |
| API网关 | Kong/Nginx | 文档中二选一描述不明确 | 明确选Nginx，小团队Kong运维成本过高 |
| 文件存储 | MinIO | 选择合理，S3兼容 | 无变更建议 |

## 3. 模块设计与接口契约

### 3.1 接口定义：良好但不完整

已定义模块的API接口遵循RESTful规范，命名清晰。但缺少：
- 请求/响应 JSON 示例（AI生成前端代码时无法确定具体数据格式）
- 统一错误响应体定义
- API版本号策略（URL中无 `/v1/` 等前缀）

### 3.2 core-api 过重

core-api 承载了用户权限、菜单管理、表单引擎、数据源管理四个模块。当表单引擎故障时，整个核心服务都受影响。

**建议**：core-api 仅保留用户权限和菜单管理。表单引擎、数据源管理独立部署。

### 3.3 服务发现方案过于简单

仅通过Docker容器名进行服务发现，未考虑：
- 服务不可用时的重试策略
- 请求超时配置
- 负载均衡（多实例场景）

## 4. 数据库设计

### 4.1 已完成部分

- 用户权限相关6张表设计完整（sys_tenants, sys_users, sys_roles, sys_user_roles, sys_resources, sys_role_permissions, sys_departments）
- 表单引擎3张表设计完整（form_definitions, form_data, form_field_mappings）

### 4.2 缺失表设计

以下模块缺少数据库表设计：
- 报表相关表（report_definitions 仅有开头）
- 知识库相关表（文档、向量分块、检索记录）
- 消息相关表（模板、发送记录、WebSocket会话）
- 审批流程表（流程定义、实例、节点、审批记录）
- Skill管理表
- 审计日志表
- 数据源配置表
- AI对话记录表

### 4.3 设计风险

- `form_data.data` JSONB 列不利于按表单字段查询和建索引，报表场景下性能有问题
- 菜单权限存在双重管理（sys_resources.type='menu' + 独立菜单权限表），模型复杂

## 5. 安全设计

### 5.1 做得好的

- AES-256-GCM 加密方案设计完整
- API Key 哈希存储 + 前缀识别
- 操作审计日志包含脱敏处理
- 安全检查清单覆盖 OWASP Top 10

### 5.2 缺失项

- API 限流仅提及"Redis计数器"，无具体规则定义
- CORS 白名单无具体配置
- JWT Refresh Token 无轮换策略说明
- 密钥管理仅有环境变量方案，无密钥轮换机制
- 未提及 SQL 注入防护的具体实现（依赖ORM但未说明）

## 6. 部署与运维

### 6.1 亮点

- 三阶段分批上线策略设计合理，非常适合AI迭代开发
- 健康检查与自动恢复机制设计完整
- 容器资源配置明确

### 6.2 缺失项

- 无集中式日志收集方案（各容器独立写本地日志）
- 无数据库定时备份策略
- 监控仅提到 Prometheus，无 Grafana Dashboard 和告警路由配置
- CI/CD 部署直接 `docker-compose up -d`，无零停机策略
- 无灰度发布/蓝绿部署方案
